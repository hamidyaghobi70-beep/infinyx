## 0. هدف، دامنه و قواعد تفسیر

هدف V3.1 تبدیل چشم‌انداز V3.0 به مبنایی قابل بررسی برای تصمیم‌گیری معماری است؛ نه صدور مجوز ساخت. این نسخه خطرها، مرزهای اعتماد، پرسش‌های طراحی و معیارهای پذیرش پیشنهادی را ثبت می‌کند.

ترتیب اعتبار:
1. مجوزهای صریح و مکتوب مالک پروژه و سیاست‌های مخزن.
2. این سند و تصمیم‌های معماری (ADR) تأییدشده.
3. اسناد چشم‌انداز و پیشنهادهای قبلی.

در صورت تعارض، هیچ‌یک از متن‌های معماری به‌تنهایی مجوز کدنویسی، اتصال ابزار، انتشار Agent، Merge، Release یا Deploy ایجاد نمی‌کند.

### دامنه Implementation HOLD

تا زمان لغو صریح و مکتوب HOLD:
- مجاز: مطالعه، ممیزی متنی، تهیه مستندات، ثبت پرسش‌ها و پیشنهادهای معماری در شاخه مستندات.
- غیرمجاز: تغییر کد اجرایی، ساخت یا اتصال سرویس، ایجاد credential عملیاتی، اجرای مهاجرت داده، اتصال ابزار واقعی، انتشار یا فعال‌سازی Agent، تغییر تنظیمات محیط‌های عملیاتی، Merge، Release و Deploy.
- ایجاد این سند یا شاخه مستندات، به‌معنای خروج از HOLD نیست.
- هر فعالیت مرزی که روشن نیست، تا اخذ مجوز جداگانه متوقف می‌ماند.

## 2. مدل مفهومی معماری: Core و Orchestration

**پیشنهاد معماری (PROPOSED):** Central Intelligence Core نقش Control Plane را دارد؛ Orchestrator در Data Plane یا لایه اجرای گردش‌کار فعالیت می‌کند و سیاست‌ها و مجوزهای خود را از Control Plane دریافت می‌کند. این تفکیک در این نسخه تصمیم قطعی نیست.

مسئولیت‌های پیشنهادی Control Plane:
- هویت کاربران، سرویس‌ها و Agentها؛
- صدور و ارزیابی سیاست‌ها و مجوزها؛
- ثبت نسخه و وضعیت Agent و ابزار؛
- سهمیه، محدودیت منابع و چرخه عمر؛
- ثبت رویدادهای مدیریتی و ممیزی.

مسئولیت‌های پیشنهادی Data Plane:
- اجرای گردش‌کار و هماهنگی Agentها؛
- اعمال محدودیت‌های زمان، تعداد گام و منابع؛
- فراخوانی ابزار فقط از مسیر Tool Gateway؛
- مدیریت وضعیت اجرا، لغو و جبران عملیات.

**اصل مرزی:** Orchestrator نمی‌تواند با تصمیم داخلی خود سیاست دسترسی را گسترش دهد. هر فراخوانی ابزار باید مستقل از متن تولیدشده توسط مدل، در مرز اعتماد معتبر احراز هویت و مجوزدهی شود.

تصمیم‌های باز: محل استقرار Orchestrator، الگوی ارتباط همگام/ناهمگام، مرز سرویس‌ها و رفتار هنگام عدم دسترسی به Control Plane. همه موارد TBD تا ثبت ADR.

## 3. Threat Model — مدل تهدید

این مدل اولیه و کیفی است؛ جایگزین ارزیابی ریسک، تست نفوذ یا بازبینی تخصصی نیست.

### 3.1 دارایی‌های مورد حفاظت
- داده‌های کاربران و Tenantها، اسناد و حافظه Agent؛
- credentialها، کلیدها، توکن‌های نشست و اسرار اتصال ابزار؛
- مجوزها، سیاست‌ها، پیکربندی و زنجیره انتشار Agent؛
- یکپارچگی اجرای گردش‌کار، سفارش‌ها و تراکنش‌ها؛
- سوابق ممیزی، داده‌های صورتحساب و مالکیت فکری؛
- دسترس‌پذیری سرویس و بودجه مصرف مدل/ابزار.

### 3.2 مرزهای اعتماد پیشنهادی
1. کاربر/کلاینت ↔ API Gateway.
2. Tenant ↔ Tenant.
3. Control Plane ↔ Data Plane.
4. Agent Runtime ↔ Tool Gateway.
5. پلتفرم ↔ ارائه‌دهنده مدل یا سرویس ثالث.
6. محیط توسعه ↔ آزمایش ↔ تولید.
7. کد/بسته/Agent منتشرشده ↔ زنجیره ساخت و استقرار.
8. کارکنان و مدیران ↔ سامانه‌های مدیریتی و داده حساس.

### 3.3 مهاجم‌ها و سناریوهای سوءاستفاده
- کاربر مخرب یا حساب تصاحب‌شده؛
- Agent یا ابزار ثالث مخرب/آسیب‌دیده؛
- prompt injection از ورودی کاربر، سند بازیابی‌شده یا خروجی ابزار؛
- سوءاستفاده از ابزار و دسترسی بیش‌ازحد؛
- تلاش برای عبور از مرز Tenant و افشای داده دیگران؛
- درخواست شبکه‌ای غیرمجاز یا SSRF از مسیر ابزار؛
- نشت داده از طریق خروجی مدل، لاگ، حافظه یا telemetry؛
- وابستگی یا بسته آلوده در زنجیره تأمین؛
- خطای پیکربندی یا سوءاستفاده داخلی؛
- حمله محروم‌سازی از سرویس و مصرف کنترل‌نشده منابع.

### 3.4 کنترل‌های دفاعی موردنیاز (PROPOSED)
- تفکیک دستورالعمل‌ها از داده‌های غیرقابل اعتماد؛ خروجی مدل به‌تنهایی مجوز اقدام نیست.
- allowlist ابزار و مقصد، اعتبارسنجی ورودی/خروجی و کنترل خروجی شبکه در Tool Gateway.
- اصل حداقل دسترسی، مجوزهای کوتاه‌عمر و بررسی مجوز در هر عملیات حساس.
- جداسازی Tenant و آزمون منفی بین‌مستأجری.
- محدودیت زمان، تعداد گام، حجم داده و هزینه اجرا.
- پالایش داده حساس در لاگ و کنترل دسترسی به سوابق ممیزی.
- اسکن وابستگی‌ها، provenance و امضای artifact در زنجیره ساخت.
- ثبت رخداد، هشدار، پاسخ به حادثه و امکان تعلیق امن Agent یا ابزار.

جزئیات پیاده‌سازی و اثربخشی همه کنترل‌ها **TBD / NOT VERIFIED** است.

## 5. ایزوله‌سازی Runtime و Tenant

### 5.1 Runtime Isolation

گزینه‌های نیازمند ارزیابی: container سخت‌سازی‌شده، microVM، sandbox مبتنی بر WASM یا ترکیب آن‌ها. انتخاب نهایی **TBD** است و باید با مدل تهدید، نیازهای سازگاری، هزینه و بار کاری تطبیق داده شود.

حداقل الزامات طراحی:
- عدم دسترسی پیش‌فرض به میزبان و فایل‌های دیگر اجراها؛
- محدودیت CPU، حافظه، زمان و فضای موقت؛
- شبکه خروجی محدود و کنترل‌شده؛
- جداسازی اسرار هر اجرا؛
- پاک‌سازی محیط موقت پس از پایان؛
- جلوگیری از دسترسی مستقیم Agent به پایگاه داده یا credentialهای عمومی پلتفرم.

### 5.2 Tenant Isolation

گزینه‌ها: پایگاه داده مشترک همراه کنترل ردیفی، schema مجزا، یا پایگاه داده مجزا. انتخاب به طبقه‌بندی داده، نیاز انطباق، هزینه و سطح ریسک وابسته است؛ فعلاً **TBD**.

معیار پذیرش پیشنهادی:
- آزمون‌های منفی خودکار برای خواندن، نوشتن، جست‌وجو، فایل، حافظه و رخدادهای Tenant دیگر؛
- آزمون مجوز در API و لایه داده؛
- نبود دسترسی بین‌مستأجری در آزمون‌های امنیتی مستقل؛
- مستندسازی استثناها و اثبات اینکه لاگ و cache نیز مرز Tenant را رعایت می‌کنند.

## 6. Execution Semantics و اثرات جانبی ابزار

تضمین «exactly once» در سامانه توزیع‌شده نباید بدون شواهد ادعا شود. رفتار تحویل و تکرار باید برای هر نوع عملیات مشخص شود.

**پیشنهاد پایه (PROPOSED):**
- پردازش پیام‌ها می‌تواند at-least-once باشد؛ مصرف‌کننده باید در عملیات پشتیبانی‌شده idempotent باشد.
- برای درخواست‌های تغییردهنده وضعیت، idempotency key و شناسه یکتای عملیات تعریف شود.
- وضعیت عملیات و نتیجه ابزار به‌صورت قابل بازیابی ثبت شود.
- برای گردش‌کارهای چندمرحله‌ای، الگوی saga و عملیات جبرانی متناسب با قابلیت ابزار ارزیابی شود.
- توقف اجرا، جلوی گام‌های بعدی را می‌گیرد؛ اما لزوماً اثر خارجی قبلی را برنمی‌گرداند.
- وضعیت نهایی باید یکی از این حالت‌ها را شفاف گزارش کند: completed، failed، cancelled، partially_completed یا compensation_required.
- عملیات غیرقابل جبران باید پیش از اجرا به تأیید متناسب با ریسک نیاز داشته باشد.

Outbox، ترتیب رخدادها، timeout، retry و سیاست جبران برای هر نوع اتصال نیازمند ADR هستند.

- حاشیه مشارکت، CAC، LTV، نرخ نگهداشت و نقطه سربه‌سر.

مقادیر عددی در این نسخه عمداً تعیین نشده‌اند؛ داده بازار، آزمایش قیمت و فرضیات مالی باید منبع‌دار باشند. تحلیل رقابتی و تمایز محصول نیز TBD است.

## 12. پیش‌نیازهای حقوقی و توکن

توکن بومی، صدور، فروش، توزیع یا تبلیغ سرمایه‌گذاری در دامنه این نسخه مجاز نیست. حوزه قضایی هدف تعیین نشده است.

پیش از هر تصمیم مرتبط، نظر حقوقی مستقل و مکتوب درباره طبقه‌بندی دارایی، اوراق بهادار/سرمایه‌گذاری، پرداخت، مالیات، حمایت مصرف‌کننده، KYC/AML، تحریم‌ها، custody، قرارداد هوشمند و الزامات تبلیغات باید اخذ شود. استاندارد فنی توکن و مدل نگهداری دارایی نیز TBD است.

این سند مشاوره حقوقی نیست و هیچ مجوزی برای عرضه یا جذب سرمایه ایجاد نمی‌کند.

## 13. معماری تصمیم‌ها و ADR

هر تصمیم مهم باید در یک ADR مستقل ثبت شود:
- شناسه و عنوان؛
- وضعیت: proposed / accepted / superseded / rejected؛
- مسئله و محدودیت‌ها؛
- گزینه‌های بررسی‌شده و پیامدها؛
- تصمیم و دلیل؛
- ریسک‌ها و برنامه بازبینی؛
- نویسنده، بازبین و تأییدکننده مجاز.

موضوعات اولیه ADR: هویت، مدل مجوز، Policy Engine، Runtime Isolation، Tenant Isolation، پایگاه داده، Event Bus، ذخیره اسرار، لاگ ممیزی، ارائه‌دهنده مدل و سیاست data residency.

## 14. نقشه راه مشروط و Definition of Done

این نقشه راه **پیشنهادی و مشروط به لغو رسمی HOLD** است؛ به‌معنای آغاز کار یا تعهد زمانی/منابع نیست.

| مرحله | خروجی مورد انتظار | معیار پذیرش پیشنهادی |
|---|---|---|
| 1. مبانی امنیت و حاکمیت | ADRهای پایه، هویت، مجوز، طبقه‌بندی داده و مدل تهدید | تصمیم‌های حیاتی دارای ADR تأییدشده؛ threat review مستقل؛ هیچ یافته Critical حل‌نشده پیش از عبور از دروازه امنیتی |
| 2. Runtime و Orchestration | چرخه عمر Agent، اجرای محدود و کنترل ابزار | آزمون‌های منفی مجوز و Tenant؛ آزمون لغو و بازیابی؛ محدودیت منابع؛ ارزیابی امنیتی مستقل |
| 3. محصولات و Marketplace | سفارش، انتشار Agent، پرداخت و پشتیبانی | آزمون end-to-end؛ سیاست اختلاف/بازپرداخت؛ کنترل نسخه؛ بررسی امنیتی و حقوقی پیش از عرضه |
| 4. Enterprise | مدیریت سازمان و جداسازی داده | آزمون نفوذ بین‌مستأجری؛ اثبات کنترل دسترسی؛ بررسی data residency و قراردادها |
| 5. گسترش بازار | API عمومی، توسعه‌دهندگان و بازارهای جدید | SLO/SLA مصوب؛ پاسخ به حادثه تمرین‌شده؛ بررسی حقوقی هر بازار؛ اقتصاد واحد دارای داده واقعی |

وابستگی‌ها: مرحله 2 به تصمیم‌های هویت، مجوز و ایزوله‌سازی مرحله 1 وابسته است؛ مرحله 3 به قابلیت اطمینان Runtime و سیاست Marketplace؛ مرحله 4 به اثبات جداسازی؛ مرحله 5 به بلوغ امنیتی، عملیاتی، حقوقی و اقتصادی وابسته است.

برآورد زمان، بودجه و اندازه تیم تا تعیین دامنه MVP و ارزیابی منابع **TBD** است. معیارهای فوق پیشنهادند و باید پیش از شروع هر مرحله تصویب شوند.

## 15. حاکمیت، RACI و استقلال بازبینی

مالک پروژه مسئول تصمیم‌های محصول و پذیرش ریسک است؛ اما تصمیم‌های حساس امنیتی، حقوقی و مالی باید شواهد و بازبینی تخصصی مستقل داشته باشند. سازوکار جانشینی و کمیته مشورتی هنوز TBD است.

| فعالیت | مالک پروژه | مجری مستندات | بازبین مستقل |
|---|---|---|---|
| تصویب چشم‌انداز و اولویت | A | R برای ثبت | C |
| تدوین مستندات | A | R | C |
| تصمیم معماری حساس | A | C | R/C تخصصی |
| ممیزی امنیتی | A برای پذیرش ریسک | I | R |
| مجوز Merge/Release/Deploy | A با مجوز صریح | I | C |

R=مسئول انجام، A=پاسخ‌گوی نهایی، C=مشورت، I=اطلاع. انتساب نقش به ابزار یا نام، اثبات وجود شخص، دسترسی، استقلال یا انجام واقعی کار نیست. استقلال ممیزی باید با اعلام تعارض منافع، دامنه دسترسی، شواهد و بازبین واجد صلاحیت مستند شود.

## 16. وضعیت شواهد و برچسب‌ها

| برچسب | حداقل شواهد لازم | تأییدکننده پیشنهادی |
|---|---|---|
| PROPOSED | شرح پیشنهاد و فرضیات | نویسنده |
| DESIGNED | سند طراحی، مرزها و ADR مرتبط | بازبین معماری |
| IMPLEMENTED | تغییرات قابل مشاهده در مخزن/محیط مشخص | بازبین فنی |
| TESTED | گزارش اجرای تست، نسخه، محیط و نتیجه | مسئول آزمون |
| VERIFIED | شواهد مستقل متناسب با ریسک، شامل بازبینی/آزمون | بازبین مستقل |
| APPROVED FOR RELEASE | مجوز رسمی و شواهد release gate | مالک مجاز انتشار |

برچسب‌ها باید برای هر قابلیت جداگانه ثبت شوند. سند طراحی به‌تنهایی شواهد پیاده‌سازی نیست؛ وجود تست بدون گزارش اجرای معتبر، TESTED محسوب نمی‌شود.

## 17. شاخص‌های موفقیت

شاخص‌ها باید پس از تعیین MVP، بار کاری و تعهدات مشتری انتخاب شوند. فهرست اولیه:
- نرخ موفقیت وظایف و نرخ خطای ابزار؛
- زمان پاسخ صدک‌های توافق‌شده؛
- دسترس‌پذیری و زمان بازیابی؛
- هزینه تمام‌شده هر وظیفه و حاشیه مشارکت؛
- رخدادهای امنیتی و زمان مهار؛
- تعداد یافته‌های امنیتی باز به تفکیک شدت؛
- نرخ خطای جداسازی Tenant (هدف پذیرش: صفر مورد تأییدشده)؛
- نرخ شکایت، بازپرداخت و حل اختلاف Marketplace.

هیچ KPI فعلی اندازه‌گیری یا تأیید نشده است.
