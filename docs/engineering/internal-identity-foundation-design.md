# Internal Identity Foundation — Implementation Notes

- **Status:** Implemented on `feat/adr-platform-foundation`; CI verification pending
- **Scope:** Initial internal-user and external-identity persistence foundation
- **Related:** ADR-0011 and `keycloak-staging-integration-design.md`

## 1. Data model

### `users`

- Stable internal UUID primary key generated by PostgreSQL.
- Creation timestamp.
- Deliberately no tenant foreign key: a person may belong to multiple tenants, and authentication identity is independent from tenant membership.
- User lifecycle and profile fields remain future decisions.

### `user_external_identities`

- UUID identity record.
- Foreign key to one internal user with `ON DELETE RESTRICT`.
- Exact provider `issuer` and opaque `subject`.
- Unique constraint on `(issuer, subject)`; one external identity can never resolve to two internal users.
- Index by internal user and creation time; one internal user may have multiple provider identities.
- Records are immutable at the database trigger boundary. The application role receives only SELECT/INSERT privileges; reassignment and deletion are not part of this phase.

These are global identity-directory tables, not tenant-owned tables. They intentionally do not use tenant RLS. Tenant membership and authorization remain separate and must be checked by the tenant authorization boundary in a later phase.

## 2. Persistence contract

Implemented in `src/persistence/internal-identities.ts`:

- `createInternalUser`: creates an internal UUID identity.
- `getInternalUser`: resolves an internal UUID.
- `linkExternalIdentity`: links a provider identity to an existing internal user. It is idempotent for the same user and returns a conflict if the identity is already linked elsewhere.
- `resolveExternalIdentity`: exact issuer/subject lookup; unknown identity returns null.

SQL values are parameterized. Persistence failures are mapped to generic errors. Issuers must be HTTPS URLs without user-info, query, or fragment; subjects remain opaque and are not normalized. No email/phone matching or implicit account linking exists.

**Trust precondition:** the caller of `linkExternalIdentity` must first establish verified control of the external identity through a trusted authentication/provisioning adapter. This phase does not implement that adapter, OIDC verification, or a public linking endpoint. The persistence function is not itself proof of identity.

## 3. Migration and compatibility

Migration `004_internal_identity_foundation.cjs` is additive. It does not rewrite `tenant_memberships.user_id`, backfill existing memberships, or infer provider identities from legacy subject values. Existing authentication, tenant transactions, invitation persistence, and membership lifecycle remain unchanged.

Rollback is intentionally refused once any internal user or external identity row exists. A data-bearing identity directory must not be dropped as an ordinary schema rollback.

## 4. CI and verification boundary

CI grants the application role SELECT/INSERT only on the two identity tables. No UPDATE or DELETE grants are provided for external identity records. Unit tests cover exact mapping, idempotency, conflicts, multiple identities, malformed issuer/subject inputs, parameterization, and generic error handling. PostgreSQL integration tests cover unique mapping, concurrent claims, foreign-key enforcement, and restricted mutation privileges.

Passing CI verifies this isolated persistence foundation only. It does not make Keycloak configured, enable authentication, migrate existing users, or establish production readiness.

## 5. Explicitly deferred

- Refactoring the trusted principal to internal `userId`.
- Separating tenant selector from authenticated identity in `withTenantTransaction` and making active membership mandatory before repository callbacks.
- Migrating tenant memberships and invitation actor attribution to internal user IDs.
- OIDC/JWKS verification, Keycloak configuration, BFF/session handling, provisioning, linking/unlinking UX, recovery, user lifecycle, and audit workflows.
- Production secret management, infrastructure, deployment, merge, and release.
